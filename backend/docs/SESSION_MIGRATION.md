# Миграция сессий (JWT stateless)

**Дата:** 11.08.2026
**Статус:** план согласован

## Суть

Таблица `sessions` (2 записи в legacy) **НЕ мигрируется** в новую систему.

### Почему
- Новая система использует **JWT-токены** (stateless) — сессии в БД не нужны
- Токены выдаются при логине, живут ~1 час (настраивается в config/jwt.php)
- Refresh-токены для продления не реализованы (v1) — при истечении нужен повторный логин

### Последствие для пользователей
При переключении на новую систему **все пользователи будут разлогинены** (их cookie `sessid` перестанет работать). Это НЕ баг, а ожидаемое поведение.

### Коммуникационный план
1. Уведомить пользователей (менеджеров, монтажников) заранее — за 2-3 дня до cutover
2. В день переключения: первый вход требует логин + пароль
3. Пароли: MD5 → при первом логине автоматически перехэшируются в bcrypt (уже реализовано в AuthController)
4. Проблем с потерей данных НЕТ — заказы и пользователи мигрированы (6749/6749)

### Технические детали
- Таблица `sessions` в новой БД остаётся (создаётся миграцией), но не используется
- JWT TTL: 60 минут (config/jwt.php → ttl)
- Логин: POST /api/auth/login → access_token (bearer)
- Middleware: auth:api

## Чек-лист cutover
- [ ] Уведомить пользователей за 2-3 дня
- [ ] Напомнить, что первый вход — с логином и паролем
- [ ] Проверить, что у всех есть пароль (нет заблокированных)
- [ ] После cutover: пользователь логинится → MD5 перехэшируется → дальше bcrypt
